# Story 5.2: dungeon-system

## Status
Draft

## Story
**As a** user,
**I want** to use my Shadow Keys to enter challenging dungeons,
**so that** I can earn exclusive rewards.

## Acceptance Criteria
1. A DungeonService is created.
2. A POST /v2/dungeons/enter endpoint is created that consumes one Shadow Key.
3. The service verifies the user meets the dungeon's stat and level requirements.
4. The service generates trials using the QuestGenerationService, applying daily modifiers.
5. The API response is asynchronous to support the bot's loading UI.

## Dev Notes

### Service Dependencies
The DungeonService requires integration with several existing systems:
- **AwakeningService**: For Shadow Key management (completed in Story 5.1)
- **QuestGenerationService**: For trial generation (available from Story 5.1)
- **ProgressionService**: For user stat and level verification
- **UserRepository**: For user profile access
- **CacheService**: For performance optimization

### Source Tree Context
Based on the hexagonal architecture pattern, implement files in these locations:
```
app/
├── api/v2/dungeons.py                    # FastAPI router
├── application/
│   ├── services/dungeon_service.py       # Core business logic
│   └── tasks/dungeon_tasks.py            # Background processing
├── domain/
│   ├── entities/dungeon.py               # Domain models
│   └── exceptions/dungeon_exceptions.py  # Custom exceptions
└── infrastructure/
    └── repositories/dungeon_repository.py # Data access
```

### Architecture Context
Follow the established hexagonal architecture patterns:
- **API Layer**: Thin controllers that delegate to services
- **Application Layer**: Business logic orchestration in services
- **Domain Layer**: Core business entities and rules
- **Infrastructure Layer**: External system adapters (database, cache)

### Technology Stack
- **FastAPI**: For REST API endpoints with automatic OpenAPI docs
- **SQLAlchemy**: For ORM and database models
- **Pydantic**: For request/response validation
- **Alembic**: For database migrations
- **Redis**: For caching dungeon states and daily modifiers
- **Sentry**: For error tracking and monitoring

### Database Schema Design
Required tables and relationships:
```sql
-- Core dungeon definitions
dungeons (id, name, description, min_level, min_str, min_end, min_tech, rewards_json)

-- Active dungeon sessions
dungeon_instances (id, user_id, dungeon_id, status, started_at, completed_at, trials_json)

-- Individual trials within dungeons
dungeon_trials (id, instance_id, trial_number, quest_data_json, status, completed_at)

-- User progress tracking
user_dungeon_progress (user_id, dungeon_id, best_completion_time, total_attempts, last_attempt)
```

### Daily Modifier System
Implement rotating daily modifiers that affect dungeon difficulty and rewards:
- **Modifier Types**: Stat boosts, XP multipliers, special trial types
- **Storage**: Redis cache with daily expiration
- **Application**: Applied during trial generation phase

### Error Handling Patterns
Implement comprehensive error handling:
```python
# Custom exceptions
class InsufficientShadowKeysError(DungeonError)
class RequirementsNotMetError(DungeonError)
class DungeonNotFoundError(DungeonError)
class DungeonInProgressError(DungeonError)

# HTTP status mapping
InsufficientShadowKeysError -> 402 Payment Required
RequirementsNotMetError -> 403 Forbidden
DungeonNotFoundError -> 404 Not Found
DungeonInProgressError -> 409 Conflict
```

### Asynchronous Processing
For Discord bot compatibility, implement async patterns:
- Immediate response with dungeon instance ID
- Background processing for trial generation
- Status polling endpoint for progress updates
- WebSocket support for real-time updates (optional)

### Integration with Existing Systems
- **Shadow Keys**: Managed by AwakeningService, stored in user profile
- **User Stats**: Retrieved from ProgressionService for requirement checks
- **Aura Updates**: Dungeon completion should trigger aura recalculation
- **Quest Generation**: Reuse existing QuestGenerationService patterns

### Performance Considerations
- Cache dungeon definitions in Redis
- Use database connection pooling
- Implement proper indexing on user_id and dungeon_id
- Consider pagination for dungeon lists
